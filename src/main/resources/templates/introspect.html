RFC 7662 says an inactive token answers {"active": false} and nothing more — revoked, expired and never-existed all look identical, so the endpoint cannot be used to probe which tokens are real.

RFC 7009 answers 200 whether or not the token existed, so a caller cannot learn anything from the status alone. The introspection above is the evidence that it actually took effect.

Revoke

Revoking the access token stops that one token. Revoking the refresh token invalidates the authorization it came from, so the access token issued alongside it dies with it. Either way this session's tokens stop working — sign in again afterwards.

Revocation is not offered for this session

Introspection above works on any token, because the authorization server lets any authenticated client ask about one. Revocation does not: it only accepts tokens issued to the client doing the asking, and answers invalid_client otherwise. These tokens belong to PKCE Demo Client, not to the client holding the secret.
