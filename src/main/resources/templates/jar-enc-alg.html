A registration the spec says is only a declaration

request_object_encryption_alg is the JWE alg a client says it may wrap its request objects with. Its sibling, request_object_signing_alg, comes with an instruction: request objects from this client must be rejected if not signed with that algorithm. This one comes with the opposite — the client "may still use other supported encryption algorithms", in the registration spec's own words. This server does not take that offer, and the page is about why.

Reading this

This server is stricter than the spec it is implementing. OpenID Connect Dynamic Client Registration says the client "MAY still use other supported encryption algorithms or send unencrypted Request Objects, even when this parameter is present" — so read literally, request_object_encryption_alg constrains nothing and rows two and four would both be fine. A declaration that constrains nothing leaves the choice of key-wrapping algorithm with whoever sent the request, which is the party you least want choosing it. The refusals here are a deliberate departure, and worth knowing is a departure.

The unencrypted row is where the spec is followed. Registering an algorithm is a statement about how a client will encrypt, not a promise that it will. The last row is a plain signed object from a client that registered RSA-OAEP-512, and it is acted on. A deployment that wants encryption to be mandatory has to say so somewhere else — that is what a profile like FAPI is for.

Matching the registration is necessary, not sufficient. The fifth row sends exactly what its client registered and is refused anyway: RSA1_5 is a real JWA algorithm that this server does not implement. A registration cannot add an algorithm to a server, and one left out of the supported set was left out on purpose — RSA1_5 is the padding Bleichenbacher's attack is about.

Only the wrapping changes. Every accepted row decrypts to the same three-part signed JWT, which is then checked exactly as an unencrypted one is — type, signature, audience, expiry. The alg decides how the content encryption key travels and nothing else, and request_object_encryption_enc would decide the other half, the way JARM's two settings divide the same work.

The asymmetry between the two registrations is real. One says request objects must be rejected if the signature algorithm does not match; the other says the client may do as it likes. Both describe the same JWT, arriving at the same endpoint, from the same client — the difference is in the spec text, not in anything about the risk.
