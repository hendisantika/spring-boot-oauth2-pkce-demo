Asking without asking

OpenID Connect Core 3.1.2.1. prompt=none is how a client asks a question it does not want the user to see: is there still a session, and may I have a token for it? The authorization server must show nothing at all — if it cannot answer without the user, it says login_required and the client decides what to do about it. This is the request behind every silent renewal in a hidden iframe.

Reading this

Spring Authorization Server implements this one. Unlike acr_values and max_age, which it does not read at all, prompt is parsed, validated and acted on: none combined with any other value is invalid_request, a consent screen that would have been shown becomes consent_required, and an unauthenticated request becomes login_required. Of the four values OidcPrompt names, though, only none does anything — the ones that ask the server to start an interaction are accepted and ignored.

The login_required it implements could never run here. Its endpoints sit behind anyRequest().authenticated() with a login entry point — the arrangement in its own sample, and in this demo. An unauthenticated request is therefore redirected to the login page several filters before the authorization server sees it, which is exactly what prompt=none forbids: the client asked a question in a hidden iframe and got a login form nobody will ever look at. PromptNoneFilter answers those requests instead, and leaves every other case to the server.

The last row is two of this demo's own rules colliding. max_age=0 says the session must be newly authenticated; prompt=none says the user may not be asked for anything. Both cannot hold, so the answer is login_required — and the freshness filter has to stand down rather than redirect to the login page it would otherwise use. A parameter that enforces something must know about the parameter that forbids the enforcement.

An error may only be sent where the client registered it. The filter looks the client up and checks the redirect_uri against the registration before sending anything to it — the same rule the authorization server applies, and the reason a refusal cannot simply be echoed back to whatever URI the request carried. Without that check, an error response is an open redirect.

Two of the specification's four errors never appear. interaction_required and account_selection_required are not in Spring Authorization Server at all. The first would be for a server that needs to show something other than a login or a consent screen; the second only means anything where a user can be signed in as several people at once, which is not this server.

Where this is really used. A single-page application loads the authorization endpoint in a hidden iframe with prompt=none every few minutes: a code means the session is alive and a fresh token is on its way, and login_required means it is gone and the user has to be sent to sign in. The session management page shows the other half of that arrangement — the iframe that says something changed, which is what prompts this request in the first place.
