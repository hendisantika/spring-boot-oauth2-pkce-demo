FAPI 2.0 security profile

FAPI 2.0 does not invent anything. It takes the mechanisms on the other pages here and says which combination is mandatory: pushed requests, PKCE, sender-constrained tokens, and client authentication that does not involve a shared secret. This page checks the running configuration against that, and reports what fails.

Reading this

PKCE FAPI Client meets every client requirement. The others do not, and that is deliberate: each exists to demonstrate a mechanism the profile happens to forbid — a public client with no authentication, a shared secret, tokens that are not sender-constrained.

The algorithm row reads the registration, not the request. FAPI 1.0 Advanced §8.6 and FAPI 2.0 §5.4.1 say the same thing about JWS — "shall use PS256 or ES256 … and shall not use none" — and a request object is a JWS. What a client registered as its request_object_signing_alg is the whole of what can ever arrive, because RFC 9101 §10.1 has this server refuse a request object signed with anything else. Most clients here registered nothing and are marked not applicable: this server would fall back to RS256, which the profile says should not be used, but that is this server's default rather than a client's declaration.

The encryption row is a different shape. FAPI 1.0 Advanced §8.6.1 is one sentence long — "For JWE, both clients and authorization servers shall not use the RSA1_5 algorithm" — so it forbids a single algorithm and lists none to choose from. Everything that is not RSA1_5 passes, which is why RSA-OAEP-256 and RSA-OAEP-512 both sit green without being named by any profile. FAPI 2.0 carries no JWE requirement at all: it keeps ID tokens out of the front channel and dropped the request object, so its own comparison table says no encryption is required there.

The last row is not a FAPI requirement at all, and says whose it is. No FAPI profile names a content encryption method — not the Baseline, not Advanced, not 2.0. §8.6.1's one prohibition is RSA1_5, which wraps the key rather than encrypting the content. What does reach the enc is RFC 8725 §3.1, which FAPI 2.0 §5.4.1 requires adherence to: "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms … The library MUST ensure that the alg or enc header specifies the same algorithm that is used". So the row does not ask whether a method is blessed — nothing blesses any of them — it asks whether the registration names one this server would actually accept. The client that registered A192CBC-HS384 fails it, and that is a registration naming something outside the supported set rather than a taste in ciphers.

Registering nothing here means nothing, not a default. The registration spec is explicit — an omitted request_object_encryption_alg means "the RP is not declaring whether it might encrypt any Request Objects", where an omitted signing algorithm really does mean RS256. Encryption here is opt-in per request, and the algorithm this server would fall back to is one the profile permits, so the blank rows hide nothing. The client that registered a content encryption method and no algorithm to wrap its key with gets its own wording: that registration is one the spec does not allow, and this server refuses its encrypted request objects outright.

The last row is a mechanism one profile required and the next one removed. FAPI 1.0 Advanced §5.2.2 had the server "require a JWS signed JWT request object passed by value with the request parameter or by reference with the request_uri parameter" — by reference was blessed. FAPI 2.0 took it out: its comparison table replaces the request object's nbf and exp claims with "request_uri has limited lifetime", for the stated reason that this "Prevents pre-generation of requests", and §5.3.2 has the client send only client_id and a request_uri whose parameters "are sent in the pushed authorization request". A pre-registered URL is neither short-lived nor pushed, so the two clients that registered one fail the row.

That switch now has a row of its own, up in the server table. No FAPI profile names require_request_uri_registration — the specification that cares is RFC 9101 §10.4.1(a), where the server "should check that the value of the request_uri parameter does not point to an unexpected location", and a registration is what makes a location expected. OpenID Connect Discovery makes the default false; it is true here, which is this server choosing to be stricter than the specification rather than following it. FAPI 2.0 reaches the same attack surface from the other side — require PAR and nothing is ever fetched — which is why that row fails while this one passes.

Both kinds of reference arrive in the same parameter. A pushed request_uri and a fetched one are told apart by scheme, not by which is which in the registration — so this row is about the fetched kind only, and a client using PAR is not failing it. Passing it also depends on a switch: with require_request_uri_registration off, a client that registered nothing could still name any https URL and have this server go and get it, so the row reads that switch live rather than assuming where it is left.

Three settings, three different meanings of "omitted". Worth reading the rows together, because they do not behave alike. An absent request_object_signing_alg means RS256, unconditionally. An absent request_object_encryption_alg means no declaration at all. An absent request_object_encryption_enc means A128CBC-HS256 — but only if an alg was registered, since the registration spec makes that default conditional on its sibling being present. A client with an alg and no enc has therefore declared a method; a client with neither has declared nothing, and the two rows say so differently.

One client passes that row and still cannot use it. The profile's list and this server's list are different lists. ES256 is on the profile's and not on this server's, so the client that registered it is doing exactly what FAPI asks and has every request object refused anyway. A green row is a statement about the registration, not a promise that the flow works. The RSA1_5 row is the mirror of it: that client fails the profile and is refused here too, so for once the profile's prohibition and this server's supported list agree.

The client rows above are only half of §8.6. It binds "both clients and authorization servers", and FAPI 2.0 §5.4.1 says not to "use or accept" none — where accepting is exactly what a supported list declares. So the server table carries the other half: request_object_signing_alg_values_supported advertises RS256 and none beside PS256, and fails. A client here can register PS256 and pass its row while the server it is talking to still accepts none from somebody else.

The encryption list beside it passes, for a reason worth noticing. §8.6.1 binds both sides exactly as §8.6 does, and request_object_encryption_alg_values_supported is [RSA-OAEP-256, RSA-OAEP-512] — no RSA1_5. The difference is not in the rules but in what each demonstration needed. Showing alg: none being accepted requires a server that accepts it; showing RSA1_5 being refused requires a server that does not. So one list had to break the profile to teach its lesson and the other had to keep it, and the client that registered RSA1_5 fails its row while the server passes this one.

The third list is there too, and it is the one no profile has an opinion about. request_object_encryption_enc_values_supported completes the trio RFC 9101 §4 names together. None of the three FAPI profiles names a content encryption method, so that row borrows the same chain the client enc rows use — RFC 8725 §3.1's "supported set of algorithms" that nothing outside may be used with — and says so in its citation rather than implying a FAPI requirement that does not exist. It passes, and the proof that the set is really closed is a row below rather than a claim above: the client that registered A192CBC-HS384 fails, because this server refuses rather than widening the set to match a registration.

That one is a gap kept on purpose. The none and RS256 entries exist because the pages demonstrating them need a server that accepts them; removing them to turn the row green would delete the demonstrations. Saying so is the point — a gap a project has decided to keep is a different thing from one it has not noticed, and a checker that cannot tell you which is which is not worth running.

The remaining server failures are real gaps rather than configuration choices: RFC 9126 §5's server-wide require_pushed_authorization_requests is off, so a client can fall back to an ordinary authorization request, and FAPI 2.0 §5.3.1 asks the server to reject those from everyone; and the issuer is plain HTTP. The iss row and the per-client PAR lock were gaps here too until they were implemented — the point of a checker that fails is that its rows can change.

A profile check that only ever passes tells you nothing. This one is worth reading because it fails.
