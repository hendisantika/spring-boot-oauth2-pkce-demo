A list of places the server is willing to go

RFC 9101 §5.2 lets a client host its request object and hand the server a URL, and §5.2.3 says the server must then send a GET to it. That is an authorization server making an outbound request because an unauthenticated browser parameter told it to, which §10.4.1 spends a section on. Its first mitigation is to "check that the value of the request_uri parameter does not point to an unexpected location" — require_request_uri_registration is the switch that turns the client's registered request_uris into that list of expected ones.

Reading this

Only the second row moves. It is a URL this application hosts and this client never registered — belonging, in fact, to another client's list. With the requirement on it is refused before any request leaves the server; with it off the server goes and fetches it, and is saved only by a later check noticing the object names somebody else. That is the entire value of the setting — not that a different object got through, but that the outbound request happened at all — and also why the default here is true while OpenID Connect Discovery's default is false.

The list is per client, not a list of URLs the server likes. The same URL is registered — to somebody else. A client that could use another client's registered URL would make the registration a formality, and the rewrite attack RFC 9101 §10.4.2 describes works by changing exactly this parameter in the browser.

Registration is necessary, not sufficient. The last two rows are on the client's own list and refused under both settings: one serves text/plain (§10.4.1 clause (b): check the media type of the response, which means fetching with an open Accept and judging what arrives) and one returns an object carrying its own request_uri, which §4 forbids and clause (d) is about — a server that followed it would be fetching recursively on a stranger's say-so. The fetch also refuses anything that is not https — except, in this demo only, a URL on this server's own origin, because nothing here is served over TLS — caps the response, times out after two seconds and does not follow redirects, since a URL that can bounce elsewhere is a URL the list no longer describes.

Nothing about verification changes. What comes back over that GET is checked exactly as an object passed by value is — type, algorithm against the registration, signature, audience, expiry, client id. Fetching decides where the bytes came from and settles nothing about whether to believe them.

The other request_uri is unaffected. A reference from the pushed endpoint is not a URL and is never fetched; RFC 9126 §5 says it works regardless of this metadata, and the page next door shows both kinds arriving in the same parameter.
