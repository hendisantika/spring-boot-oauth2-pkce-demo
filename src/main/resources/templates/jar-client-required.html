One client's door, locked from the inside

RFC 9101 §10.5 defines require_signed_request_object twice: once as server metadata, which locks every door at once, and once as client metadata, which is this. The difference is not only scope — client metadata is registered, so a client can ask for the lock itself at registration time without the server operator deciding anything about anybody else.

Reading this

This is the same defence, at a different blast radius. The server switch is a decision about every client, including ones registered years ago by people who have left. The client setting is a decision about one client, taken by whoever registers it, and a deployment that can enumerate its clients usually turns the lock this way — one at a time, as each client learns to send request objects.

The registration endpoint had to be taught this. Spring Authorization Server's registration converters have a field for every metadata name they know and drop the rest, so require_signed_request_object arrived at the endpoint and went nowhere. Both converters are replaced here: one to keep the value on the registration, the other to echo it back in the response. Without the second half a caller cannot tell a server that understood it from one that ignored it.

Two registrations that cannot both be satisfied. The second client asked for require_signed_request_object and registered request_object_signing_alg: none — so its unsigned objects are refused by the defence, and its signed ones are refused for not being the algorithm it registered. Nothing it sends can work. Neither rule is wrong; the registration is, and a server that silently picked one of them to ignore would be hiding that from whoever has to debug it.

Two things the registration asked for and did not get. These clients asked for token_endpoint_auth_method: none and came back client_secret_basic with a generated secret: OidcClientRegistrationRegisteredClientConverter handles client_secret_post, client_secret_jwt and private_key_jwt, and everything else — none included — falls to an else branch. They also asked for no scopes, because this server refuses a registration that asks for authority beyond the initial access token's. Neither changes what this page is about, and both are the sort of thing worth noticing before building on a registration response you did not read.

The middle refusal is not the defence. The locked client's unsigned object is refused for the algorithm it did not register, not for require_signed_request_object — it never reaches that check. Two rules can refuse the same request, and which one spoke is the difference between "sign this" and "sign this differently".
