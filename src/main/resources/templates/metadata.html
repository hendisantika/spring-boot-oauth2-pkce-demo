Six fields name the client parameter they govern. A client parameter can never be a row here — these documents describe the server, and request_object_signing_alg is something a client registers — but several of these fields exist precisely to tell a client what it may register, and the pairing is most of what they mean.

For the three algorithm lists, RFC 9101 §4 says why in one sentence. It is the section already cited in the Defined by column of those rows, and it names all six values together: "The client determines the algorithms used to sign and encrypt Request Objects. The algorithms chosen need to be supported by both the client and the authorization server. The client can inform the authorization server … request_object_signing_alg, request_object_encryption_alg, and request_object_encryption_enc. Likewise, the authorization server can inform the client … request_object_signing_alg_values_supported, …" Two halves of one agreement, and RFC 9101 §10.1 then has this server refuse a request object that used anything other than the one that client chose — so the published list is not advice, it is the set the agreement may be drawn from.

The counterparts cite OpenID Connect Registration §2 rather than §4, which is deliberate: §4 names the three client parameters but attributes them to RFC 7591, and it is Registration §2 that actually defines them — the defaults, and the sentence saying a client "MAY still use other supported encryption algorithms or send unencrypted Request Objects" that this server chooses to be stricter than. The remaining two pairings are the same word at both ends, defined twice by their own RFC, and require_request_uri_registration is the odd one: not a counterpart but the field that decides whether a client's request_uris are needed at all.

Four fields are all RFC 8414 actually demands: issuer, authorization_endpoint, token_endpoint and response_types_supported. Everything past that is a decade of later specifications each registering what it needed — the device flow, pushed requests, DPoP, certificate binding, rich authorization details — which is why the document is a fair summary of what this demo can do.

Reading this

Spring Authorization Server publishes only what it knows about. The CIBA grant, the authorization_details types this demo validates, the iss parameter it now returns and the scopes its clients are registered for are all additions made by this application — and they go into both documents, from one place, so the two cannot drift apart.

The issuer here is not an https URL. RFC 8414 section 2 requires one, so a client that enforces the specification would refuse this document before reading a field of it. The same gap the FAPI page reports. The issuer is an https URL, as RFC 8414 section 2 requires.

Metadata is a promise, not proof. Nothing here is signed, and a client that fetched it over a connection it could not trust would be believing whatever it was handed — which is why the transport, and the issuer check above, do the work that the document itself cannot.
