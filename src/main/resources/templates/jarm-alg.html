Which key signs the answer

JARM signs the authorization response; which algorithm it signs with is not the server's choice but the client's, recorded on its registration as authorization_signed_response_alg. Three clients here differ in that one setting and in nothing else.

Reading this

The algorithm belongs to the registration, not the request. A client cannot ask for one per authorization request, and that is deliberate: the point of the setting is that the client knows in advance what it will have to verify, so an answer signed with anything else is refused before it is read rather than trusted because it arrived.

Omitting it means RS256. JARM gives the setting that default, so the first client — which says nothing — still gets a signature. A default of "no signature" would make the whole mode opt-out by accident.

none is not a value this can take. JARM forbids it outright: a response mode whose entire purpose is a signature cannot be satisfied by an unsigned JWT. A server that accepted the value would be promising something it was not doing — so the third client is answered with an error in the clear instead, and the page says plainly that this is a registration that cannot be honoured rather than a request that failed.

The server has to have the key. Supporting ES256 meant adding a P-256 key beside the RSA one, because the encoder picks by algorithm and cannot invent a curve. A registration naming an algorithm the server has no key for is in exactly the same position as none: refused, for the same reason.

Spring Authorization Server has no setting for this, because it has no JARM. ClientSettings carries arbitrary named settings, though, so the value lives there and the filter reads it — which is also how a real deployment would extend a registration ahead of the library catching up.
