What the server will check, not what you may send

RFC 9101 §4 says the client "can inform the authorization server of the algorithms that it supports" through request_object_signing_alg, and that "likewise, the authorization server can inform the client" through request_object_signing_alg_values_supported. Two lists, pointing in opposite directions — and an algorithm has to be on both before a request object signed with it is acted on. This page takes each advertised value and sends one.

Reading this

The list is a capability, not a permission. The second row sends PS256, which is on the list, from a client that registered RS256 — and is refused. Discovery tells a client what this server is able to check; its own registration tells it what it agreed to send. Reading the first as the second is the mistake the page is built around, and it is an easy one: the metadata is the more visible of the two.

Neither condition alone is enough. Row three sends the same PS256 that was just refused, from the client that registered it, and is acted on. Row five sends ES256 from a client that registered ES256 and publishes a key on the right curve — a perfectly ordinary algorithm, correctly signed, refused because this server does not advertise checking it. Two rows, two directions, and one rule.

none is on the list. OpenID Connect Registration allows it as a registered value, so a server that accepts it has to say so — and this one does, in a list of algorithms it checks, for a value that means there is nothing to check. The unsigned page is about what remains when the signature goes.

The other two lists were missing. RFC 9101 §4 names the encryption algorithm and method lists in the same breath as the signing one. Both were implemented here — the algorithms and the methods — and neither was published until this page. A client could only discover them by sending something and being told no, which is what discovery documents exist to prevent.

Spring Authorization Server advertises none of the three, having no notion of the request parameter at all. Every value here is added by ServerMetadataCustomizer, and derived from the same constants the filter enforces rather than from a list kept beside them — a document that can drift from the code it describes is worse than no document.
