A client that registers itself

RFC 7591. Every other client in this demo was written into configuration by hand. This one arrives at runtime with a JSON document describing itself and is handed back a client_id, a secret, and a token for managing its own registration afterwards. The interesting part is not that it works — it is everything the server refuses along the way.

Read back from the stored registration, not from the response. The client asked for neither PKCE nor consent and got both: the security posture is the server's decision, not the registering party's. And it has no scopes, because it was not allowed to ask for any — registration hands out an identity, not authority.

Reading this

Spring Authorization Server implements OpenID Connect Registration, which is RFC 7591 with OpenID's additions, at /connect/register. It is off by default, and switching it on is the entire configuration — the endpoint, the client.create scope check and the registration access token all come with it.

A token with too much scope is refused. The endpoint wants exactly client.create, so a token that also carries client.read is rejected as invalid_token rather than accepted and narrowed. Surprising the first time, and the reason the registrar here asks for one scope at a time.

The scope field is refused outright. RFC 7591 section 2 defines it, and this server rejects any registration that sets it — a client that could name its own scopes would be granting itself authority. That is a deliberate deviation from the specification, on by default, and it means a newly registered client needs something out of band before it can ask for anything.

Anything registered here is permanent. Every run adds a row to the same table the hand-written clients live in, and RFC 7592's delete operation is not implemented here, so the only way back is the database. Worth knowing before pointing this at anything that matters.
