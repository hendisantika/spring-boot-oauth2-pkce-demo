The other half of the pair

request_object_encryption_alg decides how the content encryption key reaches the server. request_object_encryption_enc decides what that key then does to the request object. They are registered separately and chosen separately, and this one comes with a default the spec writes down itself: if an algorithm is registered and a method is not, the method is A128CBC-HS256.

Reading this

The shape column is the only part of this a wire observer could check. CBC encrypts in blocks and pads the payload up to a boundary, so its ciphertext is longer than what went in and its IV is 16 bytes. GCM is a stream cipher with a 12-byte nonce and no padding at all, so its ciphertext is exactly as long as the payload. Both carry a 16-byte tag, for different reasons — CBC's is a truncated HMAC computed after the fact, GCM's falls out of the encryption itself. The unsupported row shows the difference: its tag is 24 bytes, because a CBC method's tag is half of whichever HMAC it names, and that one names SHA-384.

This default is the spec's, not this server's invention. Unlike request_object_encryption_alg, where the "default" here is a deliberate tightening, the registration text says outright that a registered algorithm with no method means A128CBC-HS256. The first row is a client that registered neither and still has a method, because of that sentence.

An unsupported method is refused, not downgraded. The fifth row sends exactly what its client registered. Falling back to something this server does offer would hand the client different cryptography from the one it asked for without saying so, which is the failure mode worth avoiding even when the substitute is stronger.

A method with no algorithm beside it is refused too. The registration spec is explicit: when request_object_encryption_enc is included, request_object_encryption_alg must be as well. The last row's client is registered the way the spec says it cannot be, and this server treats that as a registration it cannot honour rather than quietly filling in the algorithm — which is what the fallback would otherwise have done.

Nothing about the plaintext changes. Every accepted row decrypts to the same three-part signed JWT and is then checked exactly as an unencrypted one is. The enc decides the wrapping and nothing else — the same division JARM's two settings make in the other direction.
