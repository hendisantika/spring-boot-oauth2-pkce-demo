Holding the operation against the grant

RFC 9396. The rich authorization request page shows a user approving a particular payment rather than a category, and the token coming back carrying what they agreed to. That is only worth something if somebody checks it. This is the other half: a resource server that reads authorization_details off the token and refuses the payments it does not cover.

Reading this

A grant is not a voucher. The last row is the first row again, and it is accepted again. RFC 9396 describes what was authorized, not how many times it may happen — nothing in the specification makes a detail single-use, and nothing in the token could record that it had been spent. A resource server that means "one payment" has to keep that count itself, the same way it always did.

There is no error code for this. RFC 9396 registers none, so the refusal uses RFC 6750 section 3.1's insufficient_scope with a description naming what exceeded the grant. It is the closest thing that exists and it is not quite right: the scope was never the problem. Compare the step-up challenge, where RFC 9470 did define an error and a client can act on it — here the client is told only that this token will not do.

The check cannot live in a filter. Whether the token permits the operation depends on the amount and the account in the request, which no SecurityFilterChain rule can see. So the chain answers only "is this token valid", and the endpoint does the rest — which is where RFC 9396 leaves it, and why a resource server that ignores the claim is indistinguishable from one that honours it until somebody tries to overspend.

An ordinary token is refused, not accepted by default. The fourth row carries a perfectly valid token for the same user and the same scopes, and asks for the payment that was approved on the other token. It fails because this endpoint treats a missing authorization_details as nothing granted rather than as nothing to check. The opposite reading is the mistake this page exists to name.

What Spring Authorization Server contributes is the carriage, not the meaning. It has no RFC 9396 support: the demo's validator refuses unknown types at the pushed request endpoint, a token customizer copies the approved array onto the token, and everything on this page reads that claim back. Nothing in the server knows an amount from an account number.
