Logging out through the browser

OpenID Connect Front-Channel Logout. The other way of telling several clients that a session ended: instead of the server calling each of them, as the back channel does, it renders a page of hidden iframes and lets the browser load them. Each one arrives at a client carrying that client's own cookies, which is the one thing a server-to-server call can never do — and the reason this mechanism fails quietly more often than it works.

Fetched by this server rather than by the browser, so no cookie goes with them. Nothing about the requests is malformed; the clients simply cannot tell who is asking, end nothing, and answer 200 — and the last one is never delivered at all. None of which matters, because the server that rendered the iframes sees none of it: a logout that worked, one that silently did nothing, and one that never arrived are the same picture from where it is standing.

Reading this

Neither half exists in Spring. Spring Authorization Server renders no logout iframes and holds no frontchannel_logout_uri; Spring Security has no endpoint to receive one. Both sides here are written out — FrontChannelLogoutService builds the document, ClientFrontChannelLogoutController answers it. Compare that with the back channel, where Spring Security had the receiving half already.

Third-party cookies are what this runs on. Every client's iframe is a cross-site request to that client, and browsers have spent years making those arrive without cookies. When that happens the client sees an anonymous request, ends nothing, and answers 200 — exactly as in the table above. It works here only because every client in this demo happens to share an origin with the server.

The server had to allow framing. Spring Security sends X-Frame-Options: DENY by default, which would have stopped the browser loading any of this. Relaxing it is the client's decision in a real deployment, and one more thing that has to be got right for a logout to reach anybody.

Four logouts now, and only one of them is reliable. Local and RP-initiated end one session each; revocation ends the tokens; back-channel tells other clients and can be checked; front-channel tells them too, and cannot.
