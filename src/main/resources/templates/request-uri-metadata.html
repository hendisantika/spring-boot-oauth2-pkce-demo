One parameter, two unrelated features

request_uri means two different things. In RFC 9101 §5.2 it is a URL the client hosts and the authorization server fetches; in RFC 9126 it is a reference the server itself handed out. OpenID Connect Discovery's request_uri_parameter_supported is about the first one only — and RFC 9126 §5 says a pushed reference is usable "regardless of other authorization server metadata such as request_uri_parameter_supported". This server does both, and one of them involves no fetching at all.

Reading this

Silence is not neutral. Omitted, these default to request_parameter_supported: false and request_uri_parameter_supported: true — so a server that publishes neither is claiming it does not read request and does fetch request_uri. This server reads both, and Spring Authorization Server advertises neither, having no notion of either parameter. The table above marks each value that differs from what silence would have claimed.

The second and third rows are the same parameter. One is a URL this server would have to go and fetch; the other is a reference it issued minutes earlier. They share a name and nothing else. A client reading request_uri_parameter_supported: false should conclude "do not host request objects for this server", not "do not push".

Which check speaks depends on the scheme. A request_uri with an http or https scheme is a URL to fetch, and is handled by the registration rules; anything else is left to the authorization server's lookup of a pushed reference, which is the check that owns those. The test is the scheme rather than the shape of a pushed reference, because RFC 9126 §4 leaves that format to the server.

require_request_uri_registration is the one that constrains fetching. It asks whether request_uri values must be pre-registered with request_uris, and this server publishes true — its default in the spec is false, which is the permissive reading of a feature that makes the server go somewhere on a browser parameter's say-so. Its own page sends the same URL under both settings.

Fetching is the door with the hinges on the outside. RFC 9101 §10.4.1 and §10.4.2 are both about it: a server that fetches a URL on a client's say-so can be aimed at a victim, and the reference itself is unsigned and rewritable in the browser. PAR gets the same job done without the server making any outbound request — which is why the lifetime page is about references rather than URLs, and why the row above that was fetched is the only row here that cost this server a connection.
