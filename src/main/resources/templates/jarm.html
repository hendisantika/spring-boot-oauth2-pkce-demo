Signing the answer

JWT Secured Authorization Response Mode. The JAR page signs the question the client asks; this signs the answer it gets back. An ordinary authorization response is a handful of loose query parameters — nothing says who sent them, nothing says who they are for, and anything that can reach the redirect URI can change them. JARM puts the whole response in one signed JWT instead.

Reading this

Spring Authorization Server does not read response_mode at all. The string appears nowhere in it. It implements the authorization code flow, where the answer always goes on the query string, so it has never needed the parameter — and a client asking for a signed response gets loose parameters with no indication that it asked for anything. That is the worst of the three possible outcomes, and the last row above is it happening.

What the signature actually protects. Three claims the loose form has no room for: iss, so a client with several authorization servers knows which one answered — the problem the mix-up page solves with a bare parameter that anything could have written; aud, so a response delivered to the wrong client means nothing; and exp, so a captured answer stops being usable. The code is protected as a side effect of all three.

The failure is signed too, and that matters. A client that cannot trust an error is no better off than one that cannot trust a code: an attacker who can rewrite error=access_denied into code=… has done the same damage either way. The third row is an ordinary refusal carried exactly like a success.

Tampering fails on the signature, not on the contents. The fourth row is the signed answer from the second with one claim rewritten. It parses; it has the right issuer, the right audience and a perfectly plausible code; and it is refused, because the signature was over the bytes that used to be there.

This is JAR pointed the other way. JAR signs the request so the server knows the question arrived as written; JARM signs the response so the client knows the answer did. A deployment that cares about one usually wants both, and FAPI asks for exactly that pair.

Three deliveries, one JWT. The signed response is identical in every mode; what differs is where it travels. query.jwt (and plain jwt, which means the same for this flow) puts it on the query string, where it reaches the client's server in the request line — and therefore its access log. fragment.jwt puts it after the #, which a browser never sends to the server at all: the response stays in the page, for script there to read. form_post.jwt puts it in no URL whatsoever — the authorization server answers with a page that submits itself, and the client reads its own request body.

Length is the practical reason for the last one. A signed response is roughly a kilobyte, and URLs have limits that vary by browser and by every proxy in between. A form post has no such ceiling, which is why it is the mode FAPI reaches for when the response object grows.
