Device authorization grant

RFC 8628, for things with no keyboard and no browser — a TV, a CLI, a set-top box. The device shows a short code; the human approves it somewhere else; the device polls until it is told what happened.

Pretend this page is a television

Requesting a device code posts client_id and scope to /oauth2/device_authorization. No secret, no redirect URI, no browser session — this page is not signed in, and does not need to be.

Scopes requested: profile email. Note the absence of openid: Spring Authorization Server answers invalid_scope for it here, because OpenID Connect is not defined over the device grant. This flow yields an access token, never an ID token.

On the device

Go to /activate and enter:

ABCD-EFGH

verification_uri_complete — the same link with the code filled in, which is what a QR code on a real device encodes.

device_code -
interval 5s
expires in 300s

Polling /oauth2/token

Waiting for approval…

Each poll sends grant_type=urn:ietf:params:oauth:grant-type:device_code with the device code. Until someone approves, the endpoint answers HTTP 400 authorization_pending — an expected step, not a failure.

The device now holds a token it obtained without ever rendering a login form. Note it was issued a refresh token: the restriction that withholds one from a public client applies to the authorization code grant, not to this one.
