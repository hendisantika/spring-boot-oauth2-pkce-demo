Certificate-bound tokens (mTLS)

RFC 8705. The client proves who it is by presenting a TLS client certificate — nothing in the request body is a credential at all. The token that comes back is bound to that certificate, so it only works over a connection presenting the same one.

How this client is registered

client_id pkce-mtls-client
Authentication self_signed_tls_client_auth The certificate is self-signed and matched against the client's published JWK Set, so there is no CA to run.
Certificate subject CN=pkce-mtls-client
Thumbprint (x5t#S256) -
jwkSetUrl /mtls-jwks.json
Token endpoint https://localhost:8443/oauth2/token A second listener, because the rest of the demo runs on plain HTTP and only this flow needs a TLS handshake. It asks for a certificate rather than demanding one, so the failing case is refused by the token endpoint instead of dropped at the connection.

Presenting the client certificate - 200 - cnf.x5t#S256 = -

Both requests send exactly the same form. The only difference is the TLS handshake, which is the point: the credential never appears in anything the application layer can leak.

The cnf.x5t#S256 above is the certificate thumbprint from the registration table — the authorization server put it in the token, tying that token to this certificate.

What the binding buys

The issued token carries cnf.x5t#S256 — the SHA-256 of the client's certificate, the same value shown above. A resource server that honours the binding will compare it against the certificate on its own TLS connection, so a copied token is useless without the private key behind that certificate.

This is the same idea as DPoP, moved down a layer: DPoP proves possession of a key with a signed header, mTLS proves it with the transport. DPoP needs nothing from the network path; mTLS needs TLS to reach the application intact.
