An answer worth keeping

RFC 9701. Introspection ordinarily answers with a bare JSON object: true of nothing in particular, addressed to nobody, signed by no one. A resource server that wants to cache that answer, hand it on, or prove later what the authorization server actually said needs more than that — so the same response can come back as a signed JWT instead, naming its issuer and its audience.

Reading this

Spring Authorization Server has no RFC 9701 support. Neither application/token-introspection+jwt nor the token_introspection claim appears anywhere in it, and OAuth2TokenIntrospectionEndpointFilter writes the JSON form unconditionally. What it does give is the hook: introspectionResponseHandler on the endpoint configurer, which is where this page's handler sits.

Nothing changes for a client that does not ask. The handler looks at Accept and delegates to the same OAuth2TokenIntrospectionHttpMessageConverter the server would have used, so the introspection page and every existing caller get byte-for-byte what they always did. The first row above is that path.

The audience is the point, not the signature. A signature says the authorization server wrote it; the aud says who it wrote it for. Rows two and three are the same question about the same token, and the answers are not interchangeable — one resource server cannot hand its introspection result to another and have it mean anything, which is exactly what you want of a cached answer.

The typ header is not decoration, and this page proves it. RFC 9701 gives the JWT its own type — token-introspection+jwt, the media type without its prefix — so that something checking only a signature and an issuer cannot be handed an introspection response and take it for an access token. The demonstration is accidental: this server's own JwtDecoder bean refuses these responses, because Spring Security's default validator chain insists on typ: JWT. Verifying them here needs a second decoder that expects the right type. A laxer first one would have been the wrong fix.

Encryption is the half this does not do. RFC 9701 also allows the response to be encrypted to the client (introspection_encrypted_response_alg), which matters because an introspection response carries scopes, a subject and often more. Signing without encrypting is the useful half here, where the transport is already private and the point is provenance.

What a resource server gains. It can keep the answer for as long as the token lives rather than asking again on every call, and it can show what it was told. Without that, a cached introspection result is a private note a resource server made to itself, indistinguishable from one it invented.
