The same lock, for every client at once

RFC 9126 defines require_pushed_authorization_requests twice. §6 is client metadata, which one client registers for itself; §5 is server metadata — "whether the authorization server accepts authorization request data only via PAR" — and applies to every client, including the ones registered years ago by people who have left. This page is the second one, and it is also the switch FAPI 2.0 §5.3.1 has been asking for.

Reading this

This is the row the FAPI page could not pass. FAPI 2.0 §5.3.1 says the server "shall reject authorization requests sent without [RFC9126]" — every client, not the willing ones — and until this switch existed there was nothing to turn. Watch the profile row follow it: that check asks the running configuration, so it went green by the configuration changing rather than by the check being rewritten.

Server metadata outranks the registration, and never the other way. The last row's client had already locked its own door, so it is refused in both columns. A client cannot register its way out of the server's rule, which is the only arrangement that makes a server-wide rule worth having.

A signed request object is still not a pushed one. The third row carries a valid JAR request object and is refused while the switch is on. The JAR switch is the same idea for the other door, and a deployment that wants both has to turn both — which is exactly what FAPI asks for.

The pushed endpoint is unaffected, and must be. A switch that refused requests at /oauth2/par as well would leave a client no way in at all. What it refuses is arriving at the authorization endpoint any other way.

What this page does is not what a deployment should do. Moving a server-wide security setting at runtime, from a web page, is a demonstration: it is global for every client while the run lasts and is put back in a finally block. A real deployment sets it in configuration, once, and publishes it in the documents so clients can see it.
