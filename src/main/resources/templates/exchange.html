Token exchange

RFC 8693. A service that receives a user's token can trade it for one of its own: narrower, aimed somewhere else, and optionally recording that the service — not the user — is the one making the call. The alternative is passing the original token onwards, which hands every downstream hop everything the user ever granted.

The act claim is what makes this delegation rather than impersonation: the token still speaks for the user, but it records which service is doing the speaking. An audit log downstream can tell the two apart.

No act claim, so nothing downstream can tell this apart from the user calling directly. That is what impersonation means, and why delegation is usually the better default.

What may_act decided

The user's token carries may_act — RFC 8693 section 4.4, a statement by the authorization server about who is allowed to become the actor for this subject. It names one service. Everything above follows from that.

Impersonation is refused outright. Not because the caller was the wrong one — it was the named one — but because it brought no actor token. A subject token that says who may act for it cannot be used by somebody acting anonymously, so may_act does not merely restrict impersonation: it converts it into delegation, and delegation leaves an act claim behind.

The second service is refused too, and its own registration is no less trusted: it holds the token exchange grant and could exchange tokens belonging to somebody else all day. What it does not have is this user's token naming it. Authority to exchange is not authority to act for any particular person.

sub stays the user throughout — the exchange never changes who the call is for. What changes is the audience and the scope: the downstream service holds a token good for its own work and nothing else, so a leak there costs less than a leak of the original. The last attempt shows that limit holding: a service cannot exchange its way into privileges its own registration does not allow, however broad the token it was handed.

One trap, found the hard way. Spring Authorization Server compares may_act against the actor token with Objects.equals, claim by claim — and an issued token's iss claim is a java.net.URL by the time it is stored, because JwtClaimsSet converts it. A may_act carrying iss as a string matches nothing, and every exchange is refused with invalid_grant — the same answer as naming the wrong actor entirely.
