An answer nobody else can read

JARM signs the authorization response, and the algorithm is the client's to choose. Signing settles who wrote the answer; it does nothing about who can read it. A signed JWT is base64, not ciphertext — the code and the state are in plain sight to anything that sees the URL. A client that minds registers authorization_encrypted_response_alg as well.

Reading this

Signed, then encrypted — the order is not a preference. JARM nests the signed JWT inside the JWE, so the signature is over the response the client will actually read. Encrypting first and signing the ciphertext would prove only that somebody signed an opaque blob, which is no statement about its contents at all.

The key is the client's, and that changes who publishes what. Everywhere else in this demo the authorization server publishes keys and clients verify against them. Encryption runs the other way: the server encrypts to a key only the client can undo, so the client publishes and the server fetches. This one's set lives at -, and the registration points there.

What it is actually for. The response travels over TLS either way, so this is not about the wire. It is about everywhere a URL goes afterwards: the browser's history, a Referer header on the next request, the client's own access log, and every proxy in between. A signed response hands the code and the state to all of them; an encrypted one hands them a blob.

The method has a default. The registration here names only alg, and enc comes out as A128CBC-HS256 — JARM's default, visible in the header above. A client that wants something else says so; one that says nothing still gets content encryption rather than none.

A client that asks for this and publishes nothing is refused, the same way a signing algorithm this server cannot produce is. There is no key to encrypt to, and sending the response in the clear instead would defeat the setting entirely.
