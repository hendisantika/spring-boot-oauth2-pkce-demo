Being told to authenticate again

RFC 9470. The step-up page shows a client deciding in advance that it wants a stronger authentication. This is the other half, and the one that happens in practice: the client has no idea, calls the operation with the token it has, and the resource server answers with a challenge naming the level it needs.

Re-authorize as it asks

Starting a second authorization request throws this session away — the demo's RestartOAuth2LoginFilter invalidates it, so you sign in again and are then asked for the second factor. You will land on the dashboard, because that is where this demo's login ends; come back here and call it again. The challenge above survives that, because it is the client's state rather than the session's.

And the loop closes

Same client, same endpoint, same user — a different token. Nothing about the operation changed; what changed is how recently and how strongly the person behind the call proved who they were. The first refusal was not a failure, it was an instruction.

Reading this

Spring Security writes no such challenge. The string insufficient_user_authentication appears in no Spring Security 7.1.1 module. Its BearerTokenAccessDeniedHandler answers 403 with insufficient_scope — RFC 6750 section 3.1 — which is the right answer to a missing scope and the wrong one here. A scope is granted once and the user cannot fix it by trying harder; an authentication level can be raised by asking them for one more factor. The status carries that difference: 401 says authenticate again, 403 says do not bother. The handler on this page is InsufficientUserAuthenticationHandler, and it exists because nothing shipped does this.

The challenge is the only way the client could know. Without it a client sees a refusal and has nothing to act on: retrying is pointless, and re-authorizing blindly means guessing which of the server's levels was wanted. Naming acr_values in the header turns a dead end into a step the user can complete. RFC 9470 section 3 defines exactly these two parameters, acr_values and max_age, for that reason.

Two servers have to agree, and neither is the client. The resource server names a level; the authorization server is the one that can raise it, which is why the client is sent back there rather than being asked for a password itself. The value travelling between them is an acr — an identifier both sides already understand — and this demo's are urn:demo:loa:1 and urn:demo:loa:2, enforced by the filter the step-up page describes.

The max_age in the challenge is not enforced here. It is sent, because RFC 9470 says a resource server may state how fresh it wants the authentication to be, and a client is meant to pass it on. Spring Authorization Server has no max_age handling at all — the parameter appears nowhere in its sources — so passing it on would change nothing, and this page does not pretend the round trip would refresh anything but the acr.
