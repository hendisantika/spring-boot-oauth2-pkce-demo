JWT-secured authorization requests

RFC 9101. The authorization request travels as a JWT the client signed, so the authorization server can tell it arrived exactly as it was written. PAR keeps the request off the front channel; JAR makes it tamper-evident wherever it travels. They compose, and for the same reason.

Where this sits

Spring Authorization Server has no notion of the request parameter — it would ignore it and act on whatever the query string said, which is precisely the attack JAR exists to stop. A filter verifies the object and then serves the request parameters from it and nothing else.

The key's location is kept in this demo's configuration rather than on the client registration, so existing registrations need no migration. A deployment would read it from the client's registered jwkSetUrl.
