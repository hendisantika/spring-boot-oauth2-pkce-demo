One way in, and it is not the browser

Pushing the authorization request sends the parameters to the server over an authenticated back channel and hands the browser a reference. That is worth nothing while the same client can also put the parameters in a query string, which is why RFC 9126 §6 defines require_pushed_authorization_requests: "whether the only means of initiating an authorization request the client is allowed to use is PAR". It is the same shape of lock as the one JAR defines, for a different door.

Reading this

The first two rows are the same request. Same parameters, same query string, same kind of confidential client — one is acted on and one is not, and the only difference is a boolean on a registration. That is the whole of what this setting does, and it is the piece the PAR page cannot show, because a demo that pushes voluntarily proves nothing about a client that would rather not.

Two checks, in order, and the page says which one spoke. The check the registration turns on asks only whether a request_uri is present — it is a check about how the request was started. Whether that reference is one this server issued, is still alive, and belongs to this client is the authorization server's own check, and the invented-reference row is refused by that one rather than by this. Two rules can refuse the same request, and knowing which is the difference between "push it" and "push it again".

A signed request object is not a pushed one. The last row carries a perfectly good JAR request object and is refused anyway. JAR stops the request being changed in the browser; PAR stops it going through the browser at all. They compose — FAPI asks for both — but neither substitutes for the other, and a client that registered this lock has not satisfied it by signing.

The server-wide half exists in the RFC and not here. RFC 9126 defines require_pushed_authorization_requests twice: §6 as client metadata, which is this page, and §5 as server metadata meaning the server "accepts authorization request data only via PAR". This server publishes the §5 value as false in both documents — accurate, and there is no switch here to make it true. FAPI 2.0 §5.3.1 asks for exactly that server-wide rejection, which is why that row on the profile page still fails.

Spring Authorization Server has no setting for this either. It travels as settings.client.require-pushed-authorization-requests, read by a filter that runs before the authorization endpoint — and, like the request object settings beside it, it is carried through the registration endpoint so a client can register for it the way RFC 9126 §6 describes.
