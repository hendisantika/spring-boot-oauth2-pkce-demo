Pushed authorization requests

RFC 9126. Instead of packing the authorization request into a redirect and hoping the browser delivers it unchanged, the client posts it to the authorization server over a back channel first and gets a handle. The browser then carries a client id and that handle, nothing more.

Try it

Signing in as PKCE Confidential Client pushes the request to /oauth2/par first — that endpoint requires client authentication, which is what makes the request tamper-proof. PKCE Demo Client has no secret, so it cannot push and sends the request the ordinary way.

Why it matters

A front-channel request can be read and rewritten by anything the redirect passes through. PKCE protects the code that comes back; it does nothing for the request going out, so scope, redirect_uri and code_challenge itself are all modifiable in transit. Pushing the request authenticated closes that: by the time the browser is involved, the server already knows exactly what was asked for.

It also sidesteps URL length limits, which is what makes richer request objects practical.
