How long ago did they prove it?

OpenID Connect Core 3.1.2.1 gives a client two questions to ask about an authentication. acr_values asks how strongly; max_age asks how recently, and the answer comes back as auth_time. A session an hour old is still a valid session — it is just not evidence that the person at the keyboard is the one who signed in.

Reading this

Spring Authorization Server does not know the word max_age. The string appears nowhere in it. The parameter is enforced by MaxAgeRequiredFilter, sitting beside the filter that enforces acr_values — two halves of one specification paragraph, neither implemented by the server.

prompt=login is validated and then ignored. The server knows the value: OidcPrompt lists none, login, consent and select_account, and it refuses a request that combines none with any of the others. But none is the only one ever acted on — answered with login_required or consent_required. The value that means do not interrupt the user is implemented; both values that ask the server to start an interaction are not.

Spring's OAuth2 client cannot send max_age either. No such string in spring-security-oauth2-client, and the authorization request it builds comes from a fixed set of parameters — so a browser client here passes it the way it already passes acr_values, through the demo's own request resolver.

Re-authenticating costs the step-up. A forced login leaves the session with one factor, so acr drops back to urn:demo:loa:1 even as auth_time moves forward. Recent and strong are genuinely different axes, which is why the step-up challenge names both in one header.

The filter takes the authentication away without touching the session. It has to: the client's own authorization request — its state and PKCE verifier — lives in that session, and invalidating it would strand the callback with authorization_request_not_found. So the security context is removed, the same URL goes round again, and the ordinary entry point asks for a password.

max_age=0 needs a guard against itself. The login it forces is moments old, so the resumed request is judged stale all over again and the browser bounces between the two for ever. The filter therefore marks the one request it has already sent back — by its state, in the session it deliberately kept — and lets that request through when it returns. Read strictly, zero has the opposite problem: an authentication that has just happened has an elapsed time of zero at any resolution, zero is not greater than zero, and the parameter would ask for nothing at all. Everyone reads it as "prove it again now", and so does this.

A pushed request would slip past it. Enforcement reads the query string at the authorization endpoint, and PAR leaves only a request_uri there — the same limitation the step-up page documents for acr_values. Enforcing either for pushed requests means checking at the push, where there is no user session yet to judge.
