What binds an ID token?

The authorization code, the refresh token and the access token can all be tied to something the client holds. The ID token cannot: no deployed specification binds one to a key. What it has instead are claims that say where it belongs — and this page takes the session's own ID token and tries to put it somewhere else.

Reading this

Omitting at_hash is allowed, and that is the uncomfortable part. OpenID Connect Core 3.1.3.6 requires it when the ID token comes from the authorization endpoint — the implicit and hybrid flows, where the access token travels through the browser — and makes it OPTIONAL when the token comes from the token endpoint over a direct connection, as it does here. Spring Authorization Server never emits it: the string at_hash appears nowhere in its sources.

Spring Security's client would not check it either. OidcIdTokenValidator.validate takes one argument, the ID token, and the access token is not among the things it can see. The reasoning holds for the code flow: both tokens arrive in one response over one TLS connection from a server the client authenticated, so there is no moment where one could be swapped for the other. It stops holding the instant anything else carries that pair — a backend handing them to a front end, a gateway, a log.

The nonce claim is a hash. Spring's client generates a nonce, sends createHash(nonce) in the authorization request, and keeps the value. The authorization server only ever sees the hash and copies it into the ID token, so the claim above is not a secret and matching it means having made that exact request.

There is no cnf, and no specification to add one to. DPoP binds access and refresh tokens; RFC 8705 binds access tokens; neither mentions ID tokens. One specification did — OpenID Connect Token Bound Authentication, which put a cnf.tbh in the ID token naming a TLS Token Binding (RFC 8471) — and it went nowhere when the browsers dropped Token Binding. An ID token is a bearer assertion about a past event, and it is meant to be short-lived and consumed once, at the client that asked for it.

What it is bound to is a session, not a key. The sid claim names the authorization server session behind this login, which is what back-channel logout uses to end the right one, and what the session iframe watches. That is the binding an ID token really has: not to a holder, but to a moment.
