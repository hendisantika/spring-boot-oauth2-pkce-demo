Hiding the question too

RFC 9101 section 6.2. A signed request object settles that the request arrived as the client wrote it. It does nothing about who can read it — and the request travels in the browser's URL, carrying whatever the client put in it. A login_hint is somebody's email address; authorization details are an amount and an account number. Encrypting the object to the authorization server keeps those out of every log the URL passes through.

Reading this

Signed then encrypted, and both still checked. The server decrypts first and then does exactly what it did before: the type, the signature against the client's published key, the audience, the expiry. Encryption says only that nobody else read the request — it says nothing about who wrote it, so the signature check is not optional once a request arrives encrypted.

The direction is the opposite of JARM's. There the server encrypts to a key the client publishes; here the client encrypts to a key the server publishes. Each party encrypts to whoever is going to read it, which is the only arrangement that makes sense and is also why both sides end up publishing a key set.

The server's encryption key is not one of its signing keys. A third key was added to /oauth2/jwks marked use: enc, and the two RS256 and ES256 keys are left alone. A client picks by that marking; a server that signed and decrypted with one key would work and would still be a habit worth not demonstrating.

Addressed elsewhere is refused, not ignored. The third row is a perfectly good request object, correctly signed, encrypted to a key this server does not hold. There is nothing to do with it but say so — and it is refused before the signature is ever looked at, because there is nothing to look at yet.

Pushing the request solves an overlapping problem. A pushed request never travels through the browser at all, so nothing in it reaches a log on the way; encryption is what protects an object that does travel that way. The two are usually deployed together, and FAPI asks for exactly that: push it, and sign it, and the browser carries a reference to something it cannot read either way.
