Two kinds of logout

Clearing the client's session and ending the session at the authorization server are separate acts. Only the second one stops the next authorization request from succeeding silently.

1. Local logout

POST /logout — Spring Security's LogoutFilter clears the SecurityContext, invalidates the session and drops the JSESSIONID. The authorization server is not told anything.

2. RP-initiated logout (OpenID Connect)

The browser is sent to the authorization server's end session endpoint with the ID token as proof of who is leaving. The server ends its own session, then redirects back to a post_logout_redirect_uri that was registered against the client.

end_session_endpoint /connect/logout
post_logout_redirect_uri /
id_token_hint - Abbreviated; the full JWT is on the Tokens page.

An unregistered post_logout_redirect_uri is rejected, so a logout link cannot be used as an open redirect.

Why both exist

After a local logout the authorization server still considers you signed in: pressing Sign in with PKCE again returns a code without prompting, because the server's session outlived the client's. RP-initiated logout is what makes the next login ask for credentials again.

In this demo the client and the authorization server are one application sharing one session, so either button ends up clearing both. Split across two deployments they are two independent sessions and the difference is visible.
