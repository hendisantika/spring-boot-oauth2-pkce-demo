Step-up authentication

Not every action needs the same assurance. A client can ask for a stronger authentication with acr_values, and the token comes back saying how strongly the user actually authenticated — acr for the level, amr for the methods that got there.

What the ID token says

acr urn:demo:loa:1
amr [pwd]

The authorization server recorded this at the moment you authenticated. A token cannot be talked into claiming more later — raising the level means getting a new one, which is what the button below does.

What this is for

A resource server that sees acr can refuse an operation the token is not strong enough for, rather than accepting any valid token for everything. RFC 9470 goes further and lets it say so in the challenge, so the client knows to re-authorize rather than simply failing.

Spring Authorization Server ignores acr_values, so a filter on the authorization endpoint enforces it. Without that a client could ask for a stronger authentication and be handed a token that quietly says otherwise.

These links use the public client rather than the PAR one: a pushed request leaves only a request_uri in the browser, so acr_values would never reach the endpoint that enforces it. Enforcing it for pushed requests means checking at the push instead — where there is no user session yet.
