Is the refresh token bound too?

RFC 9449 binds an access token to a key, which the DPoP page shows. Section 5 goes further: a refresh token issued to a public client must be bound to that key as well — a client with no credentials has nothing else to prove it is the one the token was issued to. This page checks whether it is.

Read those in order. The first is the binding working: a proof from a key the tokens were never tied to is refused. The second is the finding — sending no proof is not refused at all. It is served, and what comes back is an ordinary Bearer token with no cnf, which is to say a stolen refresh token is worth what it would be if none of this existed.

The third is what that costs. The same key that worked a moment ago is now refused, and the reason the server gives is jkt claim is missing: the check compares the proof against the current access token's cnf.jkt, and the unbound token issued in the second row is now the current one. One request without a proof does not merely slip past the binding — it removes it from the authorization, and the client still holding the key is the one locked out.

Every request without the bound key was refused, which is what section 5 asks for.

Reading this

The check is conditional, and that is the whole problem. OAuth2RefreshTokenAuthenticationProvider verifies the proof's key against the current access token's cnf.jkt — but only if a proof was sent, and only for a client authenticating with none. No proof means no comparison, and the request is served as though DPoP had never been involved. RFC 9449 section 5 is not conditional: a public client's refresh token is bound, and a refresh request without a matching proof is to be refused.

The binding lives on the access token, not on the refresh token. That is what makes the third row above possible. There is nowhere in the stored authorization that says "this refresh token belongs to key K" — the check reaches for the current access token and reads its cnf, so replacing that token replaces the binding. Anyone who can spend the refresh token once without a proof takes the binding off it for good.

For a confidential client there is nothing to check, and that is correct. The client authenticates with a secret, so the server already knows who is asking; the binding adds nothing the credential does not already give. The rule exists for clients that have no credential at all — which is why this page had to reach for the device grant to find one.

The device grant needed a small fix to ask the question. A public client could be issued a refresh token here and then had no way to use it: Spring Authorization Server has no client authentication for a public client's refresh request, so it was bounced to the login page. The converter that already covered the device endpoints now covers this one too — see the device page for the rest of that story.

Code binding ties the authorization code to the same key, and DPoP ties the access token. A chain that holds at every step but this one is only as strong as this step.
