The algorithm that is not one

request_object_signing_alg can be registered as none, and then the request object is a JWT with an empty signature. Reading the specifications in order is an odd experience: RFC 9101 §4 says the claims are "signed or signed and encrypted", §6.1 says decrypting one yields "a signed Request Object" — and then §10.5 spends a security consideration defining a switch to turn unsigned ones off, which is only worth writing if they are otherwise on. OpenID Connect Dynamic Client Registration settles it in five words: the value none MAY be used.

Reading this

Accepting none is not the same as accepting anything. The second row is a properly signed RS256 object from the client that registered none, and it is refused — the registration is an agreement about what will arrive, and a better object than the one agreed is still not the one agreed. The third row is the same rule pointing the other way. none is a value in that agreement, not an escape from it.

What is left doing the work. Strip the signature and a request object still buys the two things it was reached for beside integrity: the parameters travel as one unit the server reads instead of the query string, and pushing it keeps it off the browser entirely. What it stops buying is any answer to "who wrote this". That is why RFC 9101 §6.3's rule — the client_id in the request and the one in the object MUST be identical — is the last row here: with a signature it is a formality, because the object could only have come from the client whose key verified it. Without one it is the only thing tying the object to the client the request names.

The encrypted row is the one worth staring at. It is confidential and it is accepted, and it proves nothing about who sent it: this server publishes its encryption key, so anyone at all can produce a JWE addressed to it. Encryption and signing answer different questions, and only one of them is "was this really the client". A JWE around an alg: none object looks like security and is not.

The defence wins over the algorithm. The fourth row's client registered none and require_signed_request_object together, which is a registration that contradicts itself. RFC 9101 §10.5 is a downgrade defence, and a downgrade defence that could be talked out of it by the thing it defends against would not be one — so it outranks the algorithm, and the same is true of the server-wide switch in the row above.

Both switches are now published. request_object_signing_alg_values_supported and require_signed_request_object appear in both discovery documents; Spring Authorization Server advertises neither, having no notion of the request parameter at all. A client that cannot discover which algorithms are accepted finds out by being refused.
