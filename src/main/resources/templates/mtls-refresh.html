A refresh token only one connection can spend

RFC 8705. The mTLS page shows an access token bound to a client certificate. This asks the longer-lived question: the refresh token outlives every access token it mints, so if it could be spent from anywhere, binding the short-lived thing buys little. Here it is spent three ways — same certificate, a different one, and none at all.

One connection out of three got a token. The refusals are both invalid_client, which is the honest answer: the other two calls were not refused as the wrong holder of a refresh token, they were refused as nobody at all.

The refresh token rotates on every use, so the successful attempt runs last and carries the token the redemption returned. The two refusals never consumed it.

Reading this

The refresh token is usable only over the right certificate — but not because anything checks a binding. The certificate is this client's credential. Every request to the token endpoint has to authenticate the client first, and for a self_signed_tls_client_auth client that means matching the presented certificate against the one on the registration. A stranger's certificate and no certificate both fail that step, before the refresh token is so much as looked at.

No cnf check runs on refresh at all. OAuth2RefreshTokenAuthenticationProvider compares the presented DPoP proof when there is one — that is what the refresh binding page is about — and has no certificate handling whatsoever. Nothing in it reads x5t#S256 off the stored access token, because it does not need to: the client was already authenticated by the transport.

Which makes the practical difference clear. Stealing this refresh token buys an attacker nothing without the private key behind the certificate — the same conclusion as DPoP, reached by a different route. Stealing a DPoP-bound refresh token buys nothing because the token is bound; stealing this one buys nothing because the client cannot be impersonated to begin with.

RFC 8705 section 4 has a case this server cannot reach. The section is about certificate-bound refresh tokens for a public client — one that presents a certificate for binding without using it to authenticate. That client would need a real cnf comparison on refresh, because nothing else would stop a thief. Here every mTLS client authenticates with its certificate, and Spring Authorization Server offers no way to bind without authenticating, so the case never arises. The page shows what this server does; it does not claim the server implements the harder half.

The certificate is the one the mTLS page uses. Both registrations point at the same published JWK set, so the same certificate authenticates two clients — the client_id in the request says which. That is a demo shortcut, not a recommendation: a certificate shared between clients means either of them can be impersonated by whoever holds the key.

One thing left unexplained. The issued access token really does carry cnf.x5t#S256 — the table above reads it out of the token — but the literal x5t appears nowhere in the Spring Authorization Server sources or any jar on the classpath that was searched. Where it is emitted was not found, so this page does not say.
