A reference worth using once

RFC 9126. Pushing an authorization request replaces a long query string with a short reference, and the reference is the whole authorization request as far as the browser is concerned. So it matters a great deal how long one lasts and how often it works: a request_uri is short-lived and single-use, and this page spends one five different ways to see which of those the server really means.

Reading this

One-time use is a deletion, not a flag. Spring Authorization Server removes the stored request the moment it is consumed — at the consent screen as well as at the redirect — so the second attempt is not refused for having been used before. It is refused because there is nothing there. Same answer, different reason, and the difference shows in the column above.

A refusal that cannot reach the client lands on the user. Every failed attempt here is answered with 400 and an error page, not with error=invalid_request at the redirect URI — because the only record of where to send that was the pushed request the server has just deleted or never had. A browser that follows a stale bookmark shows the user a bad request; the client learns nothing and simply never hears back.

The expiry is enforced by deleting it too. An expired reference is removed before the error is returned, so a client that keeps retrying is not merely refused repeatedly — the first refusal is what clears the row.

Editing the expiry cannot help, and the reason is elegant. The value the server stores the request under is the random part and the expiry, joined. Move the expiry a year out and the reference no longer names anything: the lookup fails before the expiry is ever compared. The number is in plain sight and tamper-evident at the same time, with no signature anywhere.

Five minutes, and nothing to configure. OAuth2PushedAuthorizationRequestUri.create() hard-codes Instant.now().plusSeconds(300); there is no setting for it on the client or the server. RFC 9126 section 2.2 leaves the lifetime to the server and suggests it be short — five minutes is a reasonable reading, but a deployment that wanted a different one would have to replace the provider.

The reference is not a secret, and does not need to be. The last attempt presents a perfectly valid one as a different client and gets nowhere: the pushed request records which client pushed it, and the authorization request has to agree. That is what makes it safe for the reference to travel through a browser in the clear.

The expiry here was moved, not waited out. The third attempt rewrites the stored request so it is keyed by an expiry a minute in the past. Waiting the real five minutes would show exactly the same thing and take five minutes; what is faked is the clock, not the check.
