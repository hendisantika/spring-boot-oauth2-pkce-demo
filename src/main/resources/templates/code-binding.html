Binding the authorization code to a key

RFC 9449 section 10. An authorization code is a bearer credential for the few seconds it lives: whoever redeems it first gets the tokens. PKCE ties it to a one-time secret; the dpop_jkt parameter ties it to the client's DPoP key instead — the same key the issued token ends up bound to, so the whole flow is held together by one private key that never leaves the client.

Run it both ways

Each run sends its own authorization request as PKCE Code Binding Client, a public client with no secret, and gets a code back at /code-binding/callback. The code is then redeemed several times over — always with the correct code_verifier. The attacker being modelled holds the code and the PKCE secret, because that is the only case where binding the code to a key adds anything at all.

Spring's OAuth2 client never sees these requests. It has no notion of dpop_jkt and would drop the parameter, so the authorization request is built and the code redeemed by hand.

It is the reason the verifier has to be kept as carefully as a secret, and the gap dpop_jkt closes by adding a second binding to a key that is never sent anywhere.

Reading this

RFC 9449 section 10 says the server must compute the thumbprint of the key in the DPoP proof and reject the token request if it does not match dpop_jkt. It does not name an error code; this server answers invalid_grant, since it is the code that cannot be redeemed.

The section also warns that the protection is only as good as the key's uniqueness: reuse one key across authorization requests and a code bound to it is redeemable by anything else holding that key. Each run here generates its own.

Spring Authorization Server stores dpop_jkt with the rest of the authorization request and then ignores it, so the check is a filter sitting in front of the token endpoint. It runs before the endpoint on purpose: a request that fails the check is turned away without the authorization code being spent, which is why the third attempt above can still succeed after the first two were refused.

Section 10.1 covers the same parameter inside a pushed request, where it travels in the POST body — see PAR. DPoP shows what the binding buys once the token has been issued, and FAPI 2.0 accepts either PKCE or dpop_jkt as the way a code is bound to its client.
