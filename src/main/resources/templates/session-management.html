Asking whether the session is still there

OpenID Connect Session Management. A client that wants to know whether the user is still signed in at the provider could re-authenticate with prompt=none every few seconds, and generate a request every time. This does it without any: the provider serves a page, the client embeds it in a hidden iframe, and the two talk by postMessage. Nothing below reaches the server at all.

The last button stands in for whatever else would change it — a sign-out in another tab, a different user, an administrator ending the session. It does not reload this page, on purpose: a client goes on holding the session state it was given, and finding that the provider no longer agrees is the entire point. What it will not tell you is which of those things happened; that is what the prompt=none round trip is for.

Reading this

Neither half exists in Spring. Spring Authorization Server emits no session_state and serves no check_session_iframe; Spring Security's client has no field for the parameter and drops it, as it dropped iss. Both halves are written out here — the iframe's script is section 3.2's pseudo-code, and the page's is section 3.1's.

The cookie has to be readable by script. The provider's iframe recomputes the hash in the browser, so the browser state cannot be HttpOnly. It is only a random value — it identifies no one and grants nothing — but it is a cookie that script can read, and that has to be a deliberate decision rather than an oversight.

Section 5.1 is unusually frank. The specification notes that browsers blocking third-party content can leave the iframe unable to read that cookie, in which case it answers changed every time — and a client that obeys the specification then re-authenticates every time, "resulting in infinite loops of re-authentications". It recommends defensive code and admits the details are out of scope. The same paragraph points out that back-channel logout is not affected.

It works here for the reason it usually does not. Client and provider share an origin in this demo, so the iframe is first-party and the cookie is there. Split them across two hosts — which is the only arrangement where any of this is useful — and you are relying on the browser to keep sending a third-party cookie.
