Proving it now, not earlier

RFC 9449 section 9. A DPoP proof says the caller holds a key. It does not say when they held it: a proof made this morning is as good as one made a second ago, so anyone who captured one has a window to use it in. A server that cares closes that window by handing out a nonce and insisting the next proof echo it back.

Reading this

Neither half of this exists in Spring Security. The strings use_dpop_nonce and DPoP-Nonce appear nowhere in its resource server, and the proof verifier in Spring Authorization Server never looks at a nonce claim — it checks the signature, the method, the URI, the token hash, the identifier and the age, and stops there. The challenge, the store and the check on this page are all this demo's.

What a nonce actually buys. Everything else in a proof is fixed by the client: it chooses the identifier, the timestamp, the method and the URI, so it can make a proof at any moment and keep it. The nonce is the one value it cannot predict, which turns "this caller has the key" into "this caller had the key just now". That matters for a proof that leaks in a log or a crash dump, and for a client whose machine an attacker has only briefly.

Single use is this server's choice, not the specification's. RFC 9449 leaves the lifetime and the reuse policy entirely to whoever issues the nonce; one good until it expires is equally conformant, and busier servers do exactly that. Spending each one here makes the third row say something rather than repeat the second.

The nonce is read before the proof is verified, deliberately. The filter parses the claim without checking the signature, because all it decides is whether to ask for a nonce — a request that gets past it still has to satisfy Spring's own verification or be refused anyway. Checking the signature first would mean a client with no nonce yet is told its proof is bad, which is true of nothing.

The authorization server can ask for one too, in exactly the same shape: RFC 9449 section 8 has the token endpoint answer 400 with use_dpop_nonce and a DPoP-Nonce header. This page does the resource server half because that is where the proof is presented over and over; the token endpoint sees one proof per grant, and the window a captured one opens there is already narrow.

The DPoP page is deliberately left alone. Its resource server accepts a proof on its own, which is the ordinary arrangement and the one worth seeing first. This is a separate endpoint so that both can be true at once.
