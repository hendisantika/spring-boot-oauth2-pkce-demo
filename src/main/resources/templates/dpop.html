Sender-constrained tokens (DPoP)

RFC 9449. A bearer token is a password: whoever holds it, wins. DPoP ties the token to a key the client keeps, so every use of it has to be signed — and a copied token is worth nothing without the private key that never left the client.

The demo trades a refresh token for a DPoP-bound one, because Spring's OAuth2 client has no DPoP support and the authorization code leg cannot carry a proof without being rebuilt by hand. You signed in as PKCE Demo Client, which is issued no refresh token.

The client generates a P-256 key pair, signs a proof for the token request, and receives an access token bound to that key. Then it calls a resource server three ways.

The second and third attempts use exactly the same access token as the first. Holding the token is not enough — and holding it plus a key is not enough either. That is what "sender-constrained" buys: stealing the token no longer gets you the account.
