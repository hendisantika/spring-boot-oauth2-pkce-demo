Signing out does not take the tokens with it

Logging out ends a session. It does not, on its own, do anything at all to the access token already issued, or to the refresh token that can mint more of them. Those are two different systems, and nothing connects them unless the client says so — with RFC 7009, the same revocation endpoint the introspection page uses.

The session is gone and the user is signed out — and a resource server handed that access token would still serve it, for as long as it has left to live. Worse, the refresh token just minted a new one after the logout, with a fresh lifetime of its own. Nothing is broken here; nothing was ever told.

Both tokens are inactive and the refresh grant has nothing to work with. Revoking the refresh token is what did most of that: it invalidates the authorization it came from, and the access token goes with it.

Reading this

Neither logout touches a token. Spring Security's /logout clears the security context, invalidates the session and drops the cookie. Spring Authorization Server's RP-initiated logout, at /connect/logout, runs a SecurityContextLogoutHandler and nothing else — that is the whole of OidcLogoutAuthenticationSuccessHandler. Ending a session and ending an authorization are separate acts.

This application now revokes on both paths. RevokingLogoutHandler is registered as a logout handler on /logout and called explicitly before the RP-initiated redirect, so signing out through the nav does the right thing. The run above with revocation is that same handler; the run without it is what the framework does unaided.

A public client cannot clean up after itself. RFC 7009 requires an authenticated client, and only lets one revoke tokens it was itself issued. Revocation here is done as pkce-confidential-client, which is why this page asks for that login — and why a client with no credentials has no way to withdraw what it holds. The introspection page shows the same asymmetry from the other side.

Short access token lifetimes are the other half of the answer. Revocation closes the window; a short expiry decides how big the window is when revocation is impossible or is never called. Neither substitutes for the other.
