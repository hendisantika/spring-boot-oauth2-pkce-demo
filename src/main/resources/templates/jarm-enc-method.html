Two settings, two different jobs

A JWE is encrypted twice over. alg says how the content encryption key is wrapped for the recipient; authorization_encrypted_response_enc says what that key then encrypts the payload with. They are chosen independently, and this page changes only the second — three registrations, identical but for one word.

Reading this

CBC pads and GCM does not. A128CBC-HS256 is AES in CBC mode with a separate HMAC, and CBC works a block at a time — so the payload is padded up to a multiple of sixteen bytes whether it needs it or not. A256GCM is a stream cipher with an authentication tag, and its ciphertext is exactly as long as what went in. That is the difference the measurements above are showing, and it is the only one visible from outside.

The initialisation vector differs too. CBC takes a sixteen-byte IV, one cipher block; GCM takes twelve, the size its counter construction is defined for. Neither is a secret — both travel in the clear as the JWE's second-to-last segment — but a reused one would be catastrophic for GCM in particular, which is why it is random per response.

Both are authenticated, by different routes. CBC gets its integrity from the HMAC named in the second half of A128CBC-HS256, computed over the ciphertext after encryption; GCM produces its tag as part of encrypting. Either way the last segment is that tag, and either way changing a byte of ciphertext makes decryption fail rather than produce rubbish.

The key lengths are not what they look like. A128CBC-HS256 needs a 256-bit content encryption key — half for AES-128, half for the HMAC — while A256GCM needs 256 bits for AES alone. The number in the name refers to the cipher, not to the key the alg has to wrap, and the wrapped key is the same size here either way because RSA-OAEP-256 output is fixed by the RSA modulus rather than by its contents.

An unsupported method is refused, not downgraded. The third registration names A192CBC-HS384 — a real JWA method this server does not offer. Falling back to one it does would give the client something other than what it registered, and without telling it; the answer comes back as an error in the clear instead, exactly as an unsupported signing algorithm does.

Nothing about the plaintext changes. Every encrypted row above carries the same signed JWT it would have carried unencrypted — a different code and state each time, because each is a separate authorization, but the same three-part JWS with the same claims and the same signature. enc decides the wrapping and nothing else.
