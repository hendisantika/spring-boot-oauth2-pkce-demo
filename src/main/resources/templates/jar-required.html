Locking the door the other requests come through

RFC 9101 §10.5 is titled "Downgrade Attack", and its first sentence is the whole problem: unless the protocol is locked down to use JAR, an attacker may simply use an RFC 6749 request instead and bypass all the protection this specification provides. Signing request objects does nothing if the server still answers the same question asked in a query string. require_signed_request_object is the lock, and as server metadata it applies to every client at once.

Reading this

The first row is the attack. An ordinary OAuth 2.0 authorization request, exactly as every page here that is not about JAR sends one — and while the switch is off it works perfectly, which is the point §10.5 is making. A client can sign its request objects beautifully and gain nothing, because nobody made it use one. The defence is not a better signature; it is refusing to answer the unsigned question at all.

Two different refusals, from the same section. The switch refuses a request with no request object and a request object with alg: none, and RFC 9101 §10.5 spells out both in consecutive sentences. They are the same hole: something that arrives carrying no signature and is acted on anyway.

The last row needs no server switch. Its client registered require_signed_request_object for itself, so its ordinary request is refused in both columns. Client metadata locks one door; server metadata locks all of them. A deployment that can enumerate its clients can do this one at a time and leave the rest of the world alone, which is usually how a lock like this actually gets turned.

Only a GET is judged. The consent screen submits a POST back to the same endpoint to continue an authorization request that was already made and already checked. Treating that as a fresh request with a missing request object would refuse the user's own approval, so the check is on the authorization request rather than on the endpoint.

What this page does is not what a deployment should do. Moving a server-wide security setting at runtime, from a web page, is a demonstration and nothing else — it is global for every client while the run lasts, and it is put back in a finally block. A real deployment sets it in configuration, once, and publishes it in the documents so clients can see it.
