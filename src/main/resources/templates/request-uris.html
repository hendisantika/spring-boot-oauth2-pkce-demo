Naming the URLs before using them

require_request_uri_registration says a request_uri must be pre-registered. request_uris is the list it must be pre-registered in — OpenID Connect Registration §2, "array of request_uri values that are pre-registered by the RP for use at the OP". This page registers two clients through the registration endpoint while you watch: one that names a URL and one that names none.

The registered URL carries a fragment, because the spec asks for one: "if the contents of the request file could ever change, these URI values SHOULD include the base64url-encoded SHA-256 hash value of the file contents referenced by the URI as the value of the URI fragment".

Reading this

The list is matched whole. Rows two and three are the same URL with a different fragment and with none, and neither is on the list. That is not this server being fussy: the spec puts a content hash in the fragment so that a server which caches the fetched file can tell a stale copy from a fresh one. A server that does not cache, like this one, still compares the whole registered string — so the effect is the same and the reason is smaller.

An empty list is a list. The last row is a client that registered no request_uris at all, pointed at a URL this application hosts and would happily serve. Registering nothing is not registering everything, and with require_request_uri_registration on it means this client cannot use the feature.

It goes out as an array and comes back as one. Spring Authorization Server's registration converters drop every metadata name they do not know, so request_uris is carried by the same pair of converters that carry the request object settings — joined into one setting on the way in, split back into a list on the way out. A caller that sent a list and read back a string would be right to wonder what had happened to it.

The https rule has a carve-out, and it applies here. RFC 9101 §5.2 says a fetched request_uri must be https. OpenID Connect Registration §2 says these URLs "MUST use the https scheme unless the target Request Object is signed in a way that is verifiable by the OP" — which is exactly what happens to every object fetched here. This demo serves no TLS, and under that clause its http URLs are within the rule rather than an exception to it.

Registering a URL is not trusting it. What comes back is still checked for its media type, for the signature against the client's key, for the audience and the expiry, and for naming the client that asked. The list settles where the server is willing to go, and nothing about what it finds there.
