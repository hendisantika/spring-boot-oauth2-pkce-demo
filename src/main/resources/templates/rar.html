Rich authorization requests

RFC 9396. A scope is a single word standing in for whatever the client wants. RAR replaces it with a structured description of the actual request — which payment, of how much, to whom — so the user approves the thing rather than the category.

The authorization server refused the request: Unsupported authorization details type Answered invalid_authorization_details at the pushed request endpoint, before anyone was asked to approve anything.

Ask for something specific

This goes out as an authorization_details parameter, pushed with the rest of the request. The consent screen shows what it means, and the issued token carries it back.

Ask for something it may not have

The server accepts only the types it implements — payment_initiation — and answers invalid_authorization_details for anything else, before the user is ever asked to approve it.

What the token says was granted

Read from the ID token of the current session (hendi), so this is the authorization server's record, not this page's memory of what it asked for.

-

A resource server reading this knows the payment was approved for that amount and that creditor. With a scope alone it would know only that something payment-shaped was allowed, and would have to trust the client about the rest.

Where this sits

Spring Authorization Server has no RFC 9396 support, so this is built on its extension points: a converter on the authorization endpoint rejects types the server does not implement, the consent screen reads the pending request to show what was asked, and a token customizer copies the approved details into the issued token.

The details are pushed rather than put in the URL. RAR requests get large quickly, which is much of why it pairs with PAR in practice.
